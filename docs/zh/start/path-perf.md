# 性能分析路径 {#sec:path-perf}

这一章回答三个问题：为什么慢、该优化哪里、优化后收益多少。前置条件是环境已跑通并能产出负载日志（见[15 分钟上手](quickstart.md#sec:get-started)）。

产物是一份带统计范围的性能报告，外加一个经过验证的优化点。方法论、完整计数器对应表与优化点分类在[性能分析与调优](../optimization/perf.md#sec:sw-perf)，本章只给诊断顺序。

## 诊断顺序

```text
静态上限 → 分阶段 → 图级占比 → 算子内部 → 指令/同步/RTL
```

顺序固定，不要跳步。低利用率只是症状，跳到 RTL 之前必须先排除软件侧原因。

### 第 1 步：算静态上限

还没上机就能算，用来判断值不值得做。估算方式与适用范围见[性能分析与调优](../optimization/perf.md#sec:sw-perf)。按计算域分组，不同精度走不同峰值。

估出来的是理论最短时间：该计算域独占峰值、没有访存和调度开销。多个计算域串行执行时下限相加，共享资源时实际时间可能更长。**它不保证端到端能达到。**

### 第 2 步：分阶段

`prefill` 与 `decode` 是两套瓶颈，必须分开统计，它们的热点排序往往不同：

| | prefill | decode |
| --- | --- | --- |
| 特征 | 计算密集 | 访存密集 |
| GEMM | 通常计算受限 | 通常访存受限 |
| attention | 瓶颈在 QK^T 计算 | 瓶颈在 KV cache 加载带宽 |

同一阶段内比较，否则数字不可比。

### 第 3 步：看图级占比

把矩阵单元的周期数与图级总周期数比一下，确认它是否值得继续深挖。

### 第 4 步：拆算子内部阶段

这一步最容易出成果。把矩阵单元的周期按阶段拆开，典型软件侧阶段有：

```text
prepare_cache      激活量化 / 缓存准备
pack_a, pack_b     操作数打包
ame_tile_call      真正驱动矩阵单元的一段
scale              量化 scale epilogue
store              结果写回
```

**关键看 `ame_tile_call` 占多少。** 它之外的阶段越大，说明瓶颈越偏软件。这一步最常见的错误是只看整体利用率就断定硬件不行——整体利用率里包含了全部软件阶段，硬件能力要看 `ame_tile_call` 那一段。

因此利用率必须写明统计范围：只统计 `ame_tile_call` 的反映硬件上限，从算子入口到返回的才是用户实际拿到的结果。把前者报成后者，会把软件阶段的损耗误记为硬件不足。

### 第 5 步：确认软件侧已收敛后再进 RTL

进入 RTL 前先排除：量化、布局搬运、scale epilogue、矩阵边缘不满一块时的处理、等待数据送达。

## 定位瓶颈

香炉峰在基线上追加了 31 个矩阵相关事件（后端池 19 个、访存池 12 个）。事件清单、`mhpmevent` 映射、计数器对应表、TMA-toolkit 用法与 Top-down 分层读法见[性能监测](../hardware/pmu.md#sec:xsai-pmu)与[性能分析与调优](../optimization/perf.md#sec:sw-perf)。

一次不可能全采。骨架必采四组：带宽利用率、各级缓存命中率、主运算单元利用率、stall 原因分解；再按热点类型定向追加；第一轮粗采、第二轮细采。
