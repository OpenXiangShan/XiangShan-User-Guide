# 软硬件协同 {#sec:co-design}

这一章面向判断某个优化该由软件还是硬件解决、要给硬件提需求，或评估某项硬件改动能给上层带来多少收益的人。

## 先查软件，再查硬件

矩阵单元的峰值算力很高，但模型实际跑出来的速度往往离峰值很远。分析时要区分两个利用率：

* **矩阵单元利用率**：只统计矩阵单元实际执行计算的那段时间（函数 `ame_tile_call`），反映硬件本身能达到的水平；
* **算子利用率**：从算子开始执行到返回的全部时间，包括数据重排、量化、反量化等软件处理，是用户实际得到的性能。

两者之间的差距通常几乎全部花在软件处理上：数据量化、数据重排（pack）、结果缩放、矩阵边缘不满一块时的处理，以及等待数据送达。所以利用率低时，先找软件把时间花在了哪里，再讨论硬件该改什么。

## 利用率低的三类原因

```text
矩阵单元利用率低
   ├── 计算：计算单元是否已经满负荷？
   ├── 访存：数据能否及时送到？
   └── 容量：数据能否放进片上缓存？
```

要逐项排查，不能只凭一个利用率数字下结论。

### 访存瓶颈：带宽受限与延迟受限

| 类型 | 表现 | 软件优化 | 硬件可提供的支持 |
| --- | --- | --- | --- |
| 带宽受限 | 需要搬运的数据总量太大 | 减少数据量：算子融合、分块、量化 | 更高带宽（HBL2）、更大片上缓存 |
| 延迟受限 | 访存次数多，或前后访存互相依赖 | 让访存与计算重叠：预取、双缓冲、软件流水 | 更多 MSHR、硬件预取、异步通路 |

数据量已经超过带宽上限时，让访存与计算重叠也没有用，只能减少数据量。提硬件需求之前，先确定属于哪一类。

## 可用的硬件支持

| 硬件特性 | 软件用法 | 相关章节 |
| --- | --- | --- |
| 原生分块尺寸（M128 × N128 × K64） | 运行时读取实际值，按读到的值生成 kernel | [数据寄存器](../isa/registers.md#sec:xsai-registers) |
| 异步执行 + 同步寄存器 | 用 `mrelease` / `macquire` 声明依赖，函数的每条返回路径都要覆盖 | [指令集扩展](../isa/instruction-set.md#sec:xsai-instruction-set) |
| 31 个矩阵相关 HPM 事件 | 判断瓶颈类型 | [性能监测](../hardware/pmu.md#sec:xsai-pmu) |
| CUTE Top-down 分析（四层） | 把停顿周期逐层分解到访存、计算、依赖及具体来源 | [性能监测](../hardware/pmu.md#sec:xsai-pmu) |
| HBL2 高带宽读通路 | 矩阵访存专用，峰值 512 B/cycle | [内存子系统与 HBL2](../hardware/memory.md#sec:xsai-memory) |
| 时钟域可配置 | 矩阵单元与核同频或异步，影响同步操作的开销 | [微架构增量](../hardware/microarchitecture.md#sec:xsai-microarchitecture) |

## 分析流程

```text
1. 按算力估算理论最短时间（不需要上机）
2. prefill 与 decode 分开统计
3. 看各算子在整个模型中的耗时占比，判断值不值得优化
4. 拆分算子内部各阶段，判断瓶颈在软件还是硬件
5. 读 HPM 计数器，判断瓶颈类型
6. 用 Top-down 分析定位具体来源
7. 提出优化方案，验证收益
```

第 1–4 步在软件侧完成，第 5–6 步用硬件计数器，第 7 步回到软件实施。确认软件处理已经优化到位后，再进入第 5 步分析硬件。各步骤的具体方法见[性能分析与调优](perf.md#sec:sw-perf)。

### 什么时候该提硬件需求

| 现象 | 结论 |
| --- | --- |
| 数据重排、缩放等软件处理耗时占比高 | 优化软件，硬件无需改动 |
| 矩阵单元利用率高，算子利用率低 | 问题在软件处理 |
| 软件处理已优化到位，`ame_tile_call` 仍占大部分时间 | 可以考虑改硬件 |
| 带宽受限，且算子融合、分块已经用足 | 可以提带宽或缓存容量需求 |
| 延迟受限 | 先做软件流水；硬件可评估预取或增加 MSHR |
| 片上缓存不够，分块开不大 | 提缓存容量需求，或改算法减少数据量 |

## 优化手段分类

| 类别 | 原理 | 典型手段 |
| --- | --- | --- |
| 提高计算密度 | 每次访存支撑更多计算 | 分块、寄存器分块、算子融合 |
| 优化访存 | 用满带宽和缓存 | 数据重排、填充对齐、预取、双缓冲 |
| 改用等价算法 | 减少计算量或访存量 | 量化、稀疏、重计算 |

**量化通常收益最大**：数据变小后，缓存占用、访存量都下降，低精度的峰值算力也更高。但量化会改变计算结果，必须用真实模型重新验证精度，具体要求见[性能分析路径](../start/path-perf.md#sec:path-perf)。
