# 性能分析与调优 {#sec:sw-perf}

这一章讲三件事：性能数字怎么测准、瓶颈属于哪一类、有哪些优化方向可用。诊断顺序与逐层拆解方法在[性能分析路径](../start/path-perf.md#sec:path-perf)，本章给方法与规则。

## 先统一统计范围

报告里的每个性能数字都要写清统计的是哪一段时间或哪一部分，否则数字之间不可比：

| 统计对象 | 含义 |
| --- | --- |
| 单 call 周期 | 一次算子调用（含同步开销）的周期数 |
| per-MAC 周期 | 除以 MAC 数，用于横向比较不同形状 |
| 整个模型 | 端到端 token/s 或 fps |

估算理论下界时统一用 `1 MAC = 2 operations`、`理论时间 = MAC × 2 / 峰值 TOPS`。这个时间是「该计算域独占峰值吞吐、没有利用率折减、没有访存和调度开销」的下界，**不是端到端保证值**。多个计算域若串行执行，下界相加；若能并行，实际关键路径可以更小；若共享片上存储、DMA、解包或调度资源，则可能更大。

向量、softmax、RoPE、mask、residual 与数据搬运不适合用 TOPS 直接估算，应单独列规模说明。

## 测量要求

* 周期数、宿主机 wall-clock 频率、端到端 tokens/s 是三种不同的量，分开记录；
* prefill 与 decode 分开，冷启动与稳态分开——它们的热点排序不同；
* 性能运行时关闭 progress / debug 日志；至少 1 次预热、3 次测量取中位数；
* 改变量化粒度、累加顺序或近似算法时，必须补算子级误差与真实模型精度回归。

## Benchmark

负载分析按**计算域**分组，而不是按算子逐个罗列，因为不同精度走的是不同的峰值算力：

| 计算域 | 典型算子 | 用哪档峰值算 |
| --- | --- | --- |
| 低比特（INT8 × INT2 等） | 量化 LLM 的 attention / MLP projection | INT8 峰值（TOPS） |
| BF16 矩阵 | Patch Conv、QK^T / AV、projector、action head | BF16 峰值（TOPS） |

按计算域分析一个负载时，每个域给出四列：

| 计算域 | MAC | 等效 operations | 峰值算力 | 未折减理论时间 |
| --- | --- | --- | --- | --- |
| 低比特 | 统计得到 | `MAC × 2` | 该精度的峰值 TOPS | `operations / 峰值` |
| BF16 矩阵 | 统计得到 | `MAC × 2` | 该精度的峰值 TOPS | `operations / 峰值` |

这样做的价值是能在**还没上机**的时候判断某个负载是否值得用矩阵单元、瓶颈落在哪个计算域，以及理论收益上限。低比特 MAC 占比需要单独盯——它决定了有多少算力能走低精度峰值。

## Profiling 工具

### 从计数器组合到瓶颈类别再到候选策略

诊断是一个两级映射：

```text
实测计数器组合 ──对照规则──▶ 瓶颈类别 ──查表──▶ 候选优化点（按预期收益排序）
```

第一级是**按计数器组合归类**：为每个瓶颈类别预先写好几组计数器特征，实测后对号入座。最小可用的对应表：

| 瓶颈类别 | 计数器特征 | 根因方向 |
| --- | --- | --- |
| 访存受限（外部内存） | 内存带宽利用率高、主运算单元利用率低、memory stall 为主 | 降流量：融合 / 分块 / 量化 / 预取 |
| 访存受限（片上） | 片上缓存命中率高但 bank 冲突多、片上带宽打满 | 改访问模式：padding、重排、向量化加载 |
| 计算受限（运算管道未满） | 运算管道利用率中等、tile 过小、启动开销占比高 | 增大 tile、融合减少 kernel 数、提占用率 |
| 计算受限（管道已满） | 运算管道接近饱和 | 已达当前精度上限；只能抬屋顶：量化、更低精度指令 |
| 特殊功能单元瓶颈 | SFU（exp / 除法等）饱和、运算管道空闲 | SFU 卸载、低精度拟合替换、算法改写 |
| 延迟暴露 | 流水线气泡多、stall 以长延迟依赖为主、占用率低 | double buffer、软件流水、增加并行度 |
| 反量化开销 | dequant 指令占比高、运算管道被标量 / 整数指令挤占 | 权重预解压、dequant 融进 GEMM epilogue |
| 负载不均 | 各核耗时方差大、存在长尾 kernel | 均衡路由、grouped GEMM、动态调度 |

第二级是**查规则库**：每个瓶颈类别挂一组候选策略，附带适用条件与预期收益排序。这是需要长期沉淀的资产。

**选 top-k 计数器事件的原则**：一次诊断不可能全采（很多计数器互斥，需要多轮 replay）。

1. 覆盖因果链关键节点：带宽利用率、各级缓存命中率、主运算单元利用率、stall 原因分解，这四组是骨架，必采；
2. 由热点类型定向追加：量化 GEMM 加采 dequant 指令计数；attention 加采 KV 加载流量与 SFU 利用率；MoE 加采 per-kernel 耗时方差；
3. 迭代收敛：第一轮粗采定位大类，第二轮针对根因方向细采。

香炉峰可用的计数器见[性能监测](../hardware/pmu.md#sec:xsai-pmu)，矩阵单元的 L0–L3 逐层分解与 `TMA-toolkit` 用法同章。

### 必须先做的前置切分

`prefill` 与 `decode` 是**两套瓶颈**，同一个算子在两个阶段需要不同处方：

| | prefill | decode |
| --- | --- | --- |
| 特征 | 计算密集，算术强度高 | 访存密集，算术强度低（权重 / KV 每步全量读） |
| GEMM | 通常 compute-bound | 通常 memory-bound（除非大 batch 连续批处理） |
| attention | 瓶颈在 QK^T 计算 | 瓶颈在 KV cache 加载带宽 |
| 主要处方 | 算子融合、tile / 流水线调优、提高运算管道利用率 | KV 量化与压缩、GQA / MLA、预取、增大有效 batch、投机解码 |

因此热点排序必须**分阶段统计**：prefill 与 decode 的热点排序往往不同，优化资源应分开投放。

## 优化点全景

所有优化点归入三大类：

1. **提升计算密度**：让每次访存支撑更多计算（算术强度上升）；
2. **优化内存访问**：让有限带宽与缓存被用满用好；
3. **算法等价替换**：改变复杂度或 IO 模式本身。

### 按资源维度分解

与上述分类正交，每个算子都可以放在**计算、通信、存储**三个维度下审视，这一视角直接指导诊断顺序。

* **计算维度**：关注单位时间能完成多少计算。运算单元利用率低**并不意味着**瓶颈在计算——通信跟不上、存储放不下，都会让运算单元等不到任务而空转。利用率低是终末症状，三个维度的病都可能表现为它，必须沿因果链追溯根因。
* **通信维度**：关注数据在不同存储介质间搬运的开销。通信瓶颈分两类，处方不同：**带宽型**（搬运总量太大，处方是减流量：融合、tiling、量化）与**延迟型**（搬运次数多或依赖链长，处方是隐藏延迟（hide latency）：预取、double buffer、软件流水）。流量超过物理带宽极限时「藏」无效，只能「减」。通信是一条层级链，所有通信优化可统一表述为：把流量推向离计算单元更近的层级。
* **存储维度**：容量决定「能不能」。典型问题：tile 能否开得够大、double buffer 能开几份、KV cache 能否容纳长上下文与大 batch、权重能否常驻。计数器信号：寄存器 spill、片上缓存占用、占用率被资源卡死、KV cache 换入换出。

三个维度相互制约、可以相互缓解：占用更多片上存储做缓存或预取，可缓解通信压力（以空间换时间）；用重计算代替存中间结果，可缓解容量压力（以时间换空间）；量化之所以性价比高，正因为数据体积缩小后存储、通信、计算三个维度同时受益。

### 循环级优化

热点算子的实现本质都是多层循环嵌套，循环变换是最基础、杠杆最大的一类优化：

| 优化点 | 原理 | 计数器信号 | 主要 trade-off |
| --- | --- | --- | --- |
| 循环分块（tiling） | 切成 tile 使工作集落入片上缓存 / 寄存器，复用最大化 | 缓存命中率低、外部内存流量高 | tile 过大→片上溢出、占用率下降；过小→效率低、启动开销占比高 |
| 循环重排（reorder） | 调整嵌套顺序，使内层遍历连续内存、外层复用已加载数据 | 命中率低、非合并访存多 | 与分块耦合，顺序改变会影响最优 tile 形状 |
| 循环融合（fusion） | 合并相邻算子的循环，一次加载完成多次计算，省掉中间结果写回再读 | kernel 数多、中间张量流量大、启动开销占比高 | 寄存器 / 片上压力增大可能降低占用率；粒度受生产者-消费者形状约束 |
| 循环拆分（splitting） | 把循环拆成多个，分别映射到不同资源或流水级 | 单 kernel 内资源利用不均、长依赖链 | 引入同步与中间存储开销 |

算子融合大部分就是两个循环的融合，直接提高计算访存比。判断是否值得的标准是：省掉的中间张量访存量与增加的片上资源压力之比。

## 调优案例

### 量化 GEMM 的反量化开销

低比特权重的 GEMM 常在计算受限之前先被反量化开销卡住：dequant 指令挤占运算管道。处方是权重预解压，或把 dequant 融进 GEMM 的 epilogue，使运算管道不被标量 / 整数指令占用。判断依据是 dequant 指令占比与运算管道实际利用率之差。

### 输入形状导致的 M 利用率不足

框架给出的形状未必适配原生 tile 尺寸。当 M 维利用率明显不足（例如卷积每次只给 8 个像素）时，把任务留在 RVV 更合算；用工作量阈值禁（见[算子库与推理框架](../software/frameworks.md#sec:sw-frameworks)）把这类任务交回框架原核。

### 同步点位置

矩阵单元与核不同频时，同步点位置会影响整体收益（见[微架构增量](../hardware/microarchitecture.md#sec:xsai-microarchitecture)）。`mrelease` / `macquire` 的放置既要覆盖所有退出分支，又要避免在循环内部频繁同步而抵消异步执行的好处。

## 常见瓶颈

* **小算子启动开销占比过高**：需要算子融合，或用工作量阈值把不值得的任务交回 RVV；
* **访存带宽利用率不足**：部分算子的有效带宽明显低于峰值；
* **tile 划分与缓冲策略影响大**：M 利用率不足时（卷积每次只给 8 个像素）应落到小核；
* **时钟配置**：矩阵单元与核不同频时，同步点位置会影响整体收益。
