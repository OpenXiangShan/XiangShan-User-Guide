# Submodules and Version Management {#sec:sdk-submodules}

`xsai-env` gathers the RTL, the simulators, the firmware, the toolchain and the validation flows under one top-level `Makefile`, but every subsystem keeps its own source of truth, toolchain assumptions and validation path, so most components are checked out as git submodules and the top-level `VERSIONS` records the pinned revision. See [SDK Layout and Directory Structure](layout.md#sec:sdk-layout) and [Workflow and Contribution](workflow.md#sec:sdk-workflow) for directory responsibilities and workflow boundaries.

## Maintaining VERSIONS

* `make versions` regenerates `VERSIONS` from the current submodule state; do not edit the file in an editor.
* Run `make versions` for every intentional root-level submodule bump. It refreshes the top-level record so that reviewers can check the pinned dependency state without reconstructing it from gitlinks; put `VERSIONS` and the gitlink into the same parent commit.
* The root bump pull request states the submodule path, the old and the new commit, the linked submodule issue or pull request, why the bump has to happen in `xsai-env`, whether `make versions` changed `VERSIONS`, and the validation run from the root workflow.
* `make update` (`Update submodules to latest`) updates the submodules themselves, whereas `make versions` only records them.

## Updating submodules

Prefer explicit path updates, and do not casually run `git submodule update --remote --recursive`: some entries in `.gitmodules` are shallow, pinned to a non-default branch, or marked `update = none`. Before opening a root pull request, check:

```bash
git status --short
git submodule status --recursive
git diff --submodule=log
```

## Order of submodule changes

A submodule change produces two different commits: the real code commit in the submodule repository, and the gitlink bump commit in `xsai-env`; the outer repository can only point at a submodule commit that can be fetched from a remote.

1. Confirm the owning repository in `.gitmodules`.
2. When the change is not purely local integration, raise and link an issue in the owning repository.
3. Create a branch inside the submodule from its configured upstream branch.
4. Commit, validate, push and open a pull request inside the submodule repository.
5. After the submodule pull request merges, update the submodule checkout inside `xsai-env`.
6. Run `make versions`.
7. Commit the gitlink bump and the `VERSIONS` update in `xsai-env`, with the validation results and a link to the submodule pull request.

Nested submodules are committed from the inside out. For a change in `XSAI/CUTE`: commit and merge in `XSAI/CUTE` first, then update the `XSAI/CUTE` gitlink inside `XSAI` and merge the `XSAI` pull request, and finally update the top-level `XSAI` gitlink inside `xsai-env`, run `make versions` and open the root bump pull request. Every layer points at a revision that is committed, pushed and reviewable in the layer below.

When a root pull request depends on an unmerged submodule pull request, keep the root pull request in draft, link the submodule pull request, state the temporary commit SHA, and do not merge the root pull request before the submodule commit has merged or stabilised; **do not commit a gitlink that points at a local-only commit**.

## Dependency direction across submodules

| Chain | Order |
| --- | --- |
| ISA and codegen contracts | `riscv-matrix-spec` → `llvm-project-ame` / `DSL/` → `software/` + `nexus-am` → `NEMU`, `qemu`, `XSAI` |
| Linux userspace bring-up | toolchain → `firmware/riscv-rootfs/apps/` → `firmware/` image assembly → `qemu` → optionally `XSAI` or a checkpoint consumer |
| Bare-metal / AM flow | toolchain → `nexus-am` runtime + apps/tests → `NEMU` or `XSAI` |
| RTL difftest flow | `NEMU` reference `.so` → `XSAI/difftest` → `XSAI/build/emu` |
| Repository checkpoint flow | `firmware/` payload + DTB → `qemu` profiling plugin → `NEMU/resource/simpoint/` clustering binary → `scripts/checkpoint.sh` orchestration → `firmware/checkpoints/` |

## Coupling scenarios involving submodules

| Scenario | Submodules involved | Handling |
| --- | --- | --- |
| Matrix ISA, intrinsic, CSR or ABI changes | `riscv-matrix-spec`, `llvm-project-ame`, `nexus-am`, `NEMU`, `qemu`, `XSAI` | Land the source-of-truth change first, then update consumers one by one, with explicit validation at each layer |
| Memory-map or reserved-memory changes | `XSAI` (`XSAI/CUTE/`), `firmware/nemu_board`, `firmware/riscv-rootfs` (`hello_xsai`) | Treat them as a firmware/platform contract change; `mk/memory.mk`, the `firmware/linux-6.18/` config assumptions and the QEMU run parameters live in the root workspace |
| Checkpoint flow changes | `qemu`, `firmware/gcpt_restore`, `NEMU` (`resource/simpoint/`) | Keep a single integration owner, since failures usually only show end to end; orchestration lives in `scripts/checkpoint.sh` and `Makefile` in the root workspace |
| Rootfs boot workload changes | `firmware/riscv-rootfs` | Treat the build in `firmware/riscv-rootfs/Makefile`, the packaging in `rootfsimg/initramfs-*.txt` and the boot invocation in `rootfsimg/init-*.sh` as one change |

All of these scenarios progress serially; see [Workflow and Contribution](workflow.md#sec:sdk-workflow) for the parallel and serial lists on the workflow side.
