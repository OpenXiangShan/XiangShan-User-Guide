# 图重画规范（ISCA 顶会学术风格）

本文件是重画《香炉峰用户手册》全部插图的唯一依据。请完整读完再动手。

---

## 0. 目标与交付物

**目标**：把手册现有插图全部重画为 **draw.io 原生源文件 + 导出 SVG**，
风格对齐 ISCA / MICRO / ASPLOS 等体系结构顶会论文的插图：
克制、精确、信息密度高、无装饰。

**每张图交付两件东西**：

| 交付物 | 路径 | 说明 |
| --- | --- | --- |
| drawio 源文件 | `figs-src/<name>.drawio` | 可编辑的唯一真源（mxGraphModel XML） |
| 导出 SVG | `docs/zh/figs/<name>.svg` | 由源文件导出，正文引用它 |

英文手册通过符号链接共用同一套图（`docs/en/figs/*` → `docs/shared/figs/*` → `docs/zh/figs/*`），
因此**图只有一套**，且必须是英文。

## 1. 硬性要求（不满足即返工）

1. **图中不得出现任何中文**。一个汉字都不要有。术语用英文，缩写在首次出现处给全称。
2. 字体统一 **Helvetica**（drawio 的 `fontFamily=Helvetica`），不允许混用其它字体。
3. **不做花哨效果**：无阴影（`shadow=0`）、无渐变、无立体感、无圆角滥用
   （`rounded=0`；仅状态/终止类节点可用小圆角）。
4. 线条一致：结构线 `strokeWidth=1`，强调/数据通路 `strokeWidth=2`。
5. 白底。导出 SVG 时不要透明背景（`--transparent` 不加）。
6. 颜色只用于**编码类别**，且必须在图内有一致含义；不得为了好看而随意上色。
7. 字号统一：分组标题 16px、主标签 14px、次级标签/注释 12px、引脚/位域 11px。
   不允许同一张图里出现第三个层级以外的字号。
8. 文本不得溢出容器、不得相互压叠。导出后必须目视确认。
9. 箭头必须是**有意义的流向**（数据流、控制流、依赖）。不允许纯装饰箭头。
10. 图的美观标准：**对齐、等距、留白充足、视觉重心稳定**。
    同层节点等高同宽，间距一致；组与组之间留白大于组内间距。

## 2. 配色（色盲友好，克制）

只使用下表颜色。同一语义在全套图中用同一颜色。

| 语义 | 填充 | 描边 | 用途 |
| --- | --- | --- | --- |
| 计算 / 数据通路 | `#DAE8F4` | `#3D6E9E` | 计算单元、流水、数据面 |
| 存储 / 内存层次 | `#E1EFD9` | `#5E8C4A` | 缓存、内存、缓冲 |
| 控制 / 配置 | `#F6E3CE` | `#B5713A` | 控制通路、配置、旁路 |
| 外部 / 宿主 / 中性 | `#EFEFEF` | `#909090` | 宿主、外部设备、非本设计部件 |
| 香炉峰新增（强调） | `#F8D7DA` | `#A94442` | 相对昆明湖 V2R2 的**新增**部分 |
| 分组容器（无填充） | `none` | `#B0B0B0`，虚线可选 | 逻辑分组 |

背景容器用 `fillColor=none` 或 `#FAFAFA`（很浅），描边 `#B0B0B0`，不用深色。

**含义编码顺序**：先用**布局**（位置、分组、大小）表达结构，颜色只作辅助。
不得仅靠颜色区分含义。

## 3. 排版原则（学术图的核心）

- **阅读顺序**：自左向右或自上而下。数据流方向在全图保持一致。
- **层次**：用嵌套矩形表达包含关系；用并列表达对等关系。
  嵌套不超过 3 层，否则拆图。
- **对齐**：同类节点左边缘/顶边缘严格对齐（在 drawio 中用相同的 x 或 y，间距取整数）。
- **间距**：节点间距 ≥ 30px；分组内边距 ≥ 20px；组间 ≥ 50px。
- **线不穿框**：连线路由绕开节点，不要横穿文字。
- **标注**：必要的维度、位宽、方向标注在**线旁**，字号 11px，颜色 `#555555`。
- 只有多子图时才用 `(a) (b) (c)` 面板标号，放在左上角。
- 图内不要写图题（标题由正文 caption 提供），也不要写 "Figure 1"。

## 3.5 为什么大多数 drawio 架构图"看起来不专业"，以及怎么避免

这一节是评审标准的核心。逐条对照检查。

### 反面清单（现有插图的问题，全部禁止）

| 问题 | 表现 | 后果 |
| --- | --- | --- |
| **默认调色板** | 直接用 drawio 的 `#dae8fc`/`#d5e8d4`/`#ffe6cc` 与默认蓝绿黄橙 | 一眼看出是"工具默认值"，最伤专业感 |
| **坐标靠估算** | 手写 XML 时凭感觉给 x/y，导致同类节点不等距、边缘不对齐 | 视觉上"松散、歪斜"，即使内容正确也显得业余 |
| **元素大小随意** | 同类模块宽高不一致、文字长短决定框大小 | 无法形成视觉节奏 |
| **连线随意穿行** | 正交线横穿其它模块或压住文字 | 阅读时视线被打断 |
| **文字塞满** | 框内文字贴边、多行不居中对齐、字号不统一 | 显得拥挤 |
| **颜色随意** | 颜色只按"好看"分配，无固定语义 | 读者无法通过颜色推断含义，信息冗余为零 |
| **空白失控** | 有的地方挤成一团、有的地方大片空白 | 视觉重心不稳 |
| **箭头无向** | 双向箭头表示"有关联" | 丢失信息，学术图不允许 |

### 正面手法（顶会论文插图的共同特征）

1. **网格化布局**：先定一个网格（如列宽 220px、行高 80px、间隙 40px），
   所有元素都落在网格上。这是"整齐"的唯一可靠来源。
   → **强烈建议用程序生成坐标**（见第 4.5 节），而不是手写数字。
2. **统一的模块尺寸**：同层模块**等宽等高**；只有语义上更重要的模块才更大，
   且大小差异要成比例（如 2:1），不要出现 1.3:1 这种"看起来是失误"的差异。
3. **视觉层次**：三级——容器（浅色/无填充 + 细描边）→ 模块（填充 + 描边）→
   标注（无框，纯文字）。层次之间用**描边粗细**和**填充有无**区分，不靠颜色堆叠。
4. **留白分层**：组内间距 < 组间间距 < 图边缘留白。例如 30 / 60 / 80。
5. **连线规范**：正交走线；同一方向的连线保持同一通道（贴齐某条 x 或 y）；
   主数据通路用 2px 实线 + 实心箭头，控制/配置用 1px 虚线 + 空心箭头。
6. **标签克制**：框内只写名称与必要的规格（如 `L2 1 MiB / 8 banks`），
   不要把解释性句子写进图里——那是正文的职责。
7. **对齐参考线**：所有同级模块的**中心线**或**左边缘**严格对齐，不能"差不多"。
8. **对称**：能对称就对称。对称是廉价且有效的专业感来源。

### 自查问句（每轮迭代都问一遍）

- 把图缩到 25% 看，还能看出结构吗？（层次是否够强）
- 遮住文字只看图形，能猜出信息流方向吗？（布局是否自解释）
- 同类模块的边缘是否严格对齐？间距是否一致？
- 是否存在任意一个"颜色没有含义"的元素？
- 是否有一处文字贴边、重叠或溢出？

## 4. drawio 生成规则

- 手写 `mxGraphModel` XML，**不要**用 Mermaid / CSV。
- 必须包含根单元格：

```xml
<mxGraphModel dx="1400" dy="900" grid="0" gridSize="10" guides="0" tooltips="0"
              connect="0" arrows="1" fold="0" page="1" pageScale="1"
              pageWidth="1400" pageHeight="900" math="0" shadow="0">
  <root>
    <mxCell id="0"/>
    <mxCell id="1" parent="0"/>
  </root>
</mxGraphModel>
```

- 每个元素 `parent="1"`，`id` 唯一。
- XML 转义：`&amp;` `&lt;` `&gt;` `&quot;`。
- **不要在 .drawio 里写 XML 注释**。
- **必须显式设置 `html=0`**：否则 drawio 用 HTML 排版标签，会引入
  `foreignObject`，而本仓库的 PDF 管线（`rsvg-convert`）会因此显示
  "Text is not SVG - cannot display" 占位文本。
- 边必须有 `<mxGeometry relative="1" as="geometry"/>` 子元素。
- 边样式基线：
  `edgeStyle=orthogonalEdgeStyle;rounded=0;html=0;endArrow=block;endFill=1;strokeWidth=2;`
  控制流可用 `dashed=1` 区分。
- 节点样式基线：
  `rounded=0;whiteSpace=wrap;html=0;fontFamily=Helvetica;fontSize=14;verticalAlign=middle;align=center;`

页面尺寸按内容设定：`pageWidth/pageHeight` 略大于内容包围盒，
所有元素坐标从 `x=40, y=40` 起，不要留过大的空白。

### 4.5 推荐：用程序生成坐标（保证对齐与统一）

手写 XML 时 x/y 靠估算，是"丑"的主因。**推荐写一个小的 Python 生成器**：
用共享的样式与布局助手产出 drawio XML，坐标由网格计算得出。

好处：
- **对齐与等距是算出来的，不是估出来的**，因此必然整齐；
- **全套 25 张图共用同一个样式模块**，观感统一成一个家族
  （这是手册插图"专业"的关键——单张好看不如一套统一）；
- 改样式只需改一处，全套同步；
- 便于按内容长度自动分配尺寸。

建议结构（放在 `figs-src/_gen/`）：

```
figs-src/_gen/
  dsl.py          # 极薄的 drawio XML DSL：box()/container()/edge()/label()，
                  # 统一字体、字号、颜色常量、网格常量
  fig_stack.py    # 每张图一个脚本，import dsl 后描述结构
  build_all.py    # 依次运行并写 figs-src/*.drawio
```

`dsl.py` 里把第 2 节的配色表和第 1 节的字号表固化为常量，
把"网格对齐"做成默认行为（例如 `grid_x(n)`、`grid_y(n)`）。

简单图（如位域图）可以直接手写 XML，但**位域图必须共用同一个绘制函数**，
否则 12 张位域图之间会参差不齐。

## 5. 工作流（每张图必须迭代 ≥3 轮）

对**每一张**图重复以下步骤：

1. **草稿**：按第 6 节该图的规格写出 `.drawio`。
2. **导出**：
   ```bash
   cd /nfs/home/leguochun/xsai-user-guide
   bash tools/figs/export.sh figs-src/<name>.drawio
   ```
3. **渲染目视检查**：
   ```bash
   bash tools/figs/render_png.sh docs/zh/figs/<name>.svg /tmp/figcheck
   ```
   然后用读图工具查看该 PNG。**必须真的看图**，不能凭 XML 想象。
4. **记录问题并修**：逐项检查并写下发现——文字是否溢出/重叠、箭头是否穿框、
   对齐是否整齐、留白是否均匀、颜色语义是否一致、是否有中文。
5. **再迭代**：至少 3 轮（草稿 → 修 → 再修 → 定稿）。每轮都要重新导出+看图。
   若某一轮没发现任何问题，说明检查不够细，请更严格地看。

**收敛标准**：连续一轮目视检查找不到任何排版或语义问题，且满足第 1 节全部硬性要求。

### 6.1 `stack-full` — AI Software/Hardware Stack
- 出处：`docs/zh/start/stack.md`（正文 8–22 行有完整层次表）
- 内容：6 层水平堆叠（自上而下：模型与应用 / 推理框架 / 算子库 / 编译器与运行时 /
  香炉峰处理器 / 外部存储与内存），每层左侧给英文名，右侧给该层具体实例
  （如推理框架层写 `llama.cpp (ggml) · MNN · NCNN`）。
- 布局：等宽等高矩形纵向堆叠，间距 14px；左侧一个竖向双箭头标注
  `abstraction`（上）/ `implementation`（下），用 11px 斜体，不要用中文。
- 颜色：按语义分层取色——模型与应用/推理框架用中性灰、算子库与编译器/运行时用控制色、
  香炉峰处理器用计算色、外部存储用存储色。
- 要点：这是"总览图"，要一眼看清分层与各层实例，信息密度高但整齐。

### 6.2 `delta-overview` — XSAI delta over Kunminghu V2R2
- 出处：`docs/zh/start/overview.md`；`docs/zh/hardware/microarchitecture.md`
- 内容：左半是基线（`Kunminghu V2R2`：标量核、乱序流水、缓存层次、向量单元），
  右半是香炉峰在其上**新增**的四件事：矩阵计算单元（CUTE）、矩阵控制通路、
  高带宽 L2（HBL2）、异步矩阵执行。
- 布局：两个大容器并排；基线容器用中性灰；右容器内新增部件用强调色（`#F8D7DA`），
  继承自基线的部件用灰色并在图例中说明 `inherited` / `new in XSAI`。
- 要点：一眼看出"哪些是继承、哪些是新增"。必须有 2 项图例。

### 6.3 `cute-subsystems` — CUTE's four subsystems
- 出处：`docs/zh/hardware/microarchitecture.md` 第 10–20 行；CUTE 设计文档
  `xsai-env1/docs/CUTE-Design-Doc/`（若可读）
- 内容：CUTE 的四个子系统及其互连：控制逻辑（control）、存储系统（storage）、
  计算引擎（compute）、接口集成（interface）。按正文给出的关系连线。
- 布局：2×2 网格，用正交连线表达数据流方向（load → compute → store）。
- 要点：这是微架构图，要专业：模块名英文全称 + 缩写，连线标注数据宽度或方向。

### 6.4 `load-compute-store` — Three-stage pipeline with double buffering
- 出处：`docs/zh/hardware/microarchitecture.md` 第 30–36 行
- 内容：Load / Compute / Store 三阶段流水，每阶段配双缓冲（double buffer）。
- 布局：三列并排（Load | Compute | Store），每列内部上方画两个缓冲槽表示双缓冲，
  下方是执行单元；阶段间用粗箭头表示数据流；底部一条时间轴表示重叠（overlap）。
- 要点：体现"三阶段可重叠"这一核心结论；时间轴的三个色块要错开排列。

### 6.5 `memory-path` — Matrix memory access path
- 出处：`docs/zh/hardware/memory.md` 第 55–70 行
- 内容：矩阵计算单元 → 访存单元（AMU）→ 两条路径：HBL2 与 外部 LLC → 内存。
  另需标出矩阵专用读通路（每 bank 512 bit）。
- 布局：左到右的数据流；HBL2 与 LLC 作为上下并排的两个层次，用存储色。
- 要点：必须能看出"矩阵到 L2 有一条专用读通路"。

### 6.6 `hpm-flow` — HPM data flow
- 出处：`docs/zh/hardware/pmu.md` 第 30–50 行
- 内容：四个来源（Frontend / Backend / MemBlock / CoupledL2）各自产生 PFEvent，
  汇入 HPerfMonitor，再写入 CSR 计数器。
- 布局：上方四个来源并排（中性色），中间汇流（多条箭头汇聚到一个宽矩形），
  下方 CSR counters（控制色）。左侧标注 `generatePerfEvent`。
- 要点：表达"多源汇聚 + 统一映射"的结构。

### 6.7 `register-map` — Matrix register / config register selection
- 出处：`docs/zh/isa/registers.md` 第 70–82 行（含 3-bit selector 说明）
- 内容：3 位选择子把 8 个矩阵寄存器与 8 个 `mcfg` 一一对应：
  `000`–`011` → `tr0`–`tr3` / `mcfg0`–`mcfg3`；`100`–`111` → `acc0`–`acc3` / `mcfg4`–`mcfg7`。
- 布局：上方一个"3-bit selector"输入，分成两组（000–011 与 100–111），
  每组下挂对应的寄存器对。用两种颜色区分 tr 组（计算色）与 acc 组（存储色）。
- 要点：编码→寄存器对的映射必须精确可读，不要画成纯装饰的分叉线。

### 6.8 `sdk-layout` — SDK components
- 出处：`docs/zh/sdk/layout.md` 第 8–20 行
- 内容：四个组件列（RTL & simulator / simulators / firmware & bring-up /
  compiler & software）建立在顶层 Makefile 之上。
- 布局：上方四列并排（各自语义色），下方一个横跨全宽的顶层 Makefile 条（控制色），
  用向下的连线表示"由 Makefile 驱动"。
- 要点：表达"统一入口驱动四类组件"。

### 6.9 `framework-seam` — Seam positions in three frameworks
- 出处：`docs/zh/software/frameworks.md` 第 80–95 行
- 内容：三个框架（MNN / NCNN / ggml）各自的接缝位置与开关：
  MNN 在函数表与算子层、NCNN 在层实现、ggml 在 buffer type 与选核策略；
  底部统一落到矩阵核（matrix kernel）。
- 布局：三列并排，每列自上而下：框架名 → 接缝层（英文名）→ 矩阵核；
  每列用不同色相但在同一明度范围，底部矩阵核用统一色表示共享。
- 要点：一眼比较"三个框架的接缝在不同层级"。这是典型的论文对比图。

### 6.10 `verify-ladder` — Verification ladder
- 出处：`docs/zh/software/simulators.md` 第 25–35 行
- 内容：验证手段的阶梯（QEMU → NEMU → gem5 → RTL simulation → FPGA），
  越往上越接近真实、越慢。
- 布局：阶梯状（右上方向递进）的五个水平条，宽度或位置体现"精度/代价"递增；
  左侧一个向上的箭头标注 `fidelity / cost`。
- 要点：阶梯的递进关系必须清晰；不要做成简单的柱状图。
